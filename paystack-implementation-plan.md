## Goal and starting point

An attendee selects an available seat, enters their name and email, reviews the order, and pays ₦2,000 on Paystack. The booking service confirms the charge, assigns the seat, and issues one ticket with PNG and PDF downloads.

The local React site already has a Node 24 booking API and SQLite database. [The API](server/index.mjs) handles checkout and payment status, [inventory](server/inventory.mjs) stores holds and tickets, and [the Paystack adapter](server/paystack.mjs) initializes checkout and verifies transactions. TypeScript and 10 booking tests passed in the reviewed launch copy. The tests used a simulated Paystack transport. Hosted checkout with David's Paystack account, webhook delivery, and launch are pending.

Paystack's dashboard is the record of charges and refunds. The booking database connects each payment reference to an attendee, seat, and issued ticket or exception. The organizer needs both records to reconcile payments.

## Hosting and domain

| Option | Decision |
| --- | --- |
| Cloudflare Workers and D1 Free | Preferred for the $0 hosting budget. Serve the React build and booking API from one HTTPS origin. Store inventory in D1 and schedule payment reconciliation with a Cron Trigger. Port the existing Node and SQLite logic and verify it within the free limits. |
| Supabase Free with a separate frontend host | Viable with Postgres transactions, server-side functions and Cron. Requires a larger backend change and separate frontend routing. Free projects can pause after one week of inactivity. |
| Paid Node host with a persistent disk | Keeps the current Node and SQLite design with less porting. Outside the current budget. Free Render loses local SQLite data on restarts, redeploys or spin-down. |

Sources: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [Supabase pricing](https://supabase.com/pricing), and [Render free hosting](https://render.com/docs/free).

## 5. Launch gates

- **Seat and ticket integrity.** Two buyers racing for the last seat produce one hold. Repeated checkout clicks, duplicate webhooks and concurrent verification yield one ticket. A late successful payment after reassignment enters organizer review. Another browser session cannot fetch a ticket it does not own.
- **Payment behavior.** Verify hosted success, cancellation, failure, delayed confirmation, and a lost browser return. Exercise provider timeouts, amount or currency mismatch, and invalid signatures using safe staging tests. Confirm Paystack can deliver to the chosen hostname.
- **Operations.** Confirm PNG and PDF exports, named organizer access, and the booking-to-Paystack reference match. Rehearse backup and restore in staging. Pause new reservations while a pending booking settles and previously issued tickets remain available. Rehearse rolling back the application while preserving the booking records.
- **Live opening.** Deploy on the approved hostname with checkout paused. After Test Mode passes and David approves the live setup, use the same dashboard handoff to configure separate live secrets and the live webhook for the production Worker. If authorized, run a controlled live smoke payment on an isolated checkout and match the charge, seat and ticket. An optional ₦100 smoke test uses separate inventory and a server-set amount.
